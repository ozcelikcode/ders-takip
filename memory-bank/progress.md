**Administrator security (24 October; owner decisions: activity log + re-confirmation for sensitive actions; two-step sign-in and encrypted backups were not chosen):**
- *Re-confirmation:* restore, reset (both kinds), role change, account deletion and administrator creation (added so a hijacked session cannot open a new administrator without a role change) require `adminPassword` on every request. There is no session window (no migration). `middleware/adminConfirmation.ts` checks the password, removes it from the request and, when wrong, returns 400 `wrongPassword` and logs `confirmationFailed`; in production a limit of 10 per 15 minutes counts only wrong attempts. Deactivation and password reset links need no confirmation (they are logged); they can be added with the same middleware if wanted.
- *Interface:* the shared `AdminPasswordField` ("Your password to confirm"); confirmation dialogs send no request with an empty password and show a warning. In user creation the field appears only when the "Administrator" role is chosen.
- *Log:* `services/adminAudit.ts`, JSON Lines, by default `admin-audit.jsonl` next to the database (`AUDIT_LOG_PATH`; Git-ignored, 0600). Not in the database: restoring a backup rewinds the database but not the log (verified by test). Every entry carries `prev` and a SHA-256 `hash`; reading re-checks the chain from the start, `integrity: { intact, brokenAt, total }`. Write order is kept by a queue in the single process; a failed write never undoes the action and is reported on the console. Entry fields: seq, time, action code, actor and target (with the username at that time, so it still reads after an account is deleted), details (role, reset type, backup number, attempted operation, changed setting names — never values) and IP. Failed sign-ins for unknown email addresses are not logged (so the log cannot be flooded).
- *Reading:* `GET /api/admin-audit?before=&limit=` (administrators only, `no-store`), Site settings › Activity log (`?section=audit`, also in the palette): newest first, "Older entries", an integrity line (a warning when broken).
- *Limit (honest note):* someone with write access to the server can rewrite the whole file consistently; the chain catches partial changes and removals in the middle. Full protection needs a copy of the log off the server (for example mirroring to `BACKUP_COPY_DIR`; not done).
- *Tests:* backend `admin-audit.test.cjs` (4): actions that need or do not need confirmation, missing, wrong and correct passwords, the password never reaching the log, sign-in entries (students and unknown addresses are not logged), setting names without values, paging, administrators only, detection of changed and removed entries, the log surviving a restore. The self-demotion and self-deletion tests now pass the password and verify the real rules (`cannotRemoveOwnAdmin`, `cannotDeleteSelf`). Frontend: the confirmation field (settings, user actions, administrator creation) and the log panel (`admin-audit.test.tsx`, 2). Browser tests: a wrong password does not change the role and the attempt shows in the log; the existing restore, reset, role and deletion scenarios enter the password; the log section is in the axe scan.

**F5 — Data import (24 October; owner decisions: empty accounts only, shared records matched by name or otherwise created as personal, measurements copied unchanged):**
- *Export version 2:* a new `references` section names the shared categories (name, colour), shared records (name, colour, category) and shared topics (name, duration, difficulty) the data points at by id. Only shared (`isGlobal`) records and shared categories are included, never another person's personal record. Version 1 files are rejected with `importOutdated`: they lack the names of shared records, so links cannot be placed ("download again from the source site").
- *Rule:* empty accounts only (no own categories, records, sessions, plans, routines, goals, tags or topic progress). There is no per-person reset, so in practice this means a new account; that is why the first step of the welcome wizard also offers "Load my data". A non-empty account gets 409 `accountNotEmpty`; a broken or unrecognised file gets 400 `importInvalid`. No migration needed.
- *Placement (one IMMEDIATE transaction, `services/accountImport.ts`):*
  - Category: a visible category with the same name (the person's own first) is reused, otherwise a personal one is created.
  - Own record: if an own or shared record with the same name exists in the same category, it is linked to it, otherwise a personal one is created. Shared records in an administrator's file are treated like shared references too (the site catalog travels with backups, not with import).
  - Shared reference: first a shared record with the same name in a category with the same name, then the only shared record with that name; if none is found, a personal record with the same name (and a personal category if needed) is created.
  - Topic: a topic with the same name in the placed record; otherwise a new topic is created only in the person's own record, and on a shared record the link is dropped.
  - Sessions, routines, plans, goals, topic progress and tags through an old id → new id map; a link with nowhere to go is dropped and counted in `unlinked`. No overlap check (historical data the source had accepted).
  - Measurement: intervals unchanged. A running or paused session arrives paused: open intervals close at the export moment (at the latest now), and an open pause starts from there (an already open pause continues). So no time is counted during the move and two sessions can never run at once.
  - Preferences are taken when they match the schema, otherwise kept (`preferences: 'skipped'`); `onboarding: 'done'` in every case.
  - After the operation the person's routines are extended to the horizon (`extendAllSeries(now, { userId })`).
- *Bulk writes:* `bulkCreate` in chunks of 500; it was verified that SQLite (sequelize 6.37.8) returns the new ids in order. `validate: true` cannot be used because of the timestamps; validation is done with the Zod schema.
- *Interface:* the shared `components/account/AccountImportButton` (choose file → read JSON → `authStore.importAccount` → every query refreshes → summary toast; dropped links and skipped preferences are reported separately; an unreadable file and a server error show an inline warning). Profile › Your data: a "Load my data" row. Welcome wizard first step: "Coming from another site?" with the same button; on success the dashboard opens.

**F4 — Tags (24 October; owner decisions: on both records and sessions, migration approved):**
- *Model:* `tags` (`Tag`: userId, name, nameKey; (userId, nameKey) unique), `course_tags` (`CourseTag`: tagId + courseId) and `session_tags` (`SessionTag`: tagId + sessionId). Links go with CASCADE when a tag, record, session or account is deleted (verified by test).
- *Personal:* each person has their own tag list. On a shared record everyone sees and changes only their own tags; one person's tags never touch another's.
- *Name rule:* leading and trailing spaces are trimmed, inner spaces collapse to one, 1–40 characters (`tagName`). Uniqueness uses `foldSearchText`: case and Turkish letter forms are ignored ("Sınav" = "SINAV" = "sinav"); a conflict is 409 `tagExists`. Another person may use the same name.
- *Migration 013-tags:* only three new tables. It was tried on a copy, then the real database was backed up (`backend/backups/pre-013-20261024-004728.sqlite`) and the migration applied. Afterwards it was verified read-only: the last `schema_migrations` entry is `013-tags`, counts match the backup, integrity ok, foreign keys clean.
- *API (`/api/tags`):*
  - `GET`: tags + `courseTags` + `sessionTags` (only the person's tags).
  - `POST`, `PUT /:id` (rename), `DELETE /:id`.
  - `PUT /courses/:courseId` and `PUT /sessions/:sessionId` (`{ tagIds }`, at most 20, no repeats): replaces the person's tags on that record or session. The record must be visible and the session the person's own; another person's tag gives 404.
- *Filter:* `GET /api/study-sessions` and `/stats` accept `tagId`. A session matches when it is tagged itself or its record is tagged (`sessionsWithTag`). Another person's tag gives 404.
- *Export and reset:* a `tags` section in the JSON export; the account reset deletes tags.
- *Interface:*
  - Records page: a "Tags" button (`TagManagerDialog`: add, rename in place, delete with confirmation) and a tag filter (client-side, by record tag).
  - Record page: `CourseTagsPanel` (saves immediately on toggle), next to the goal panel.
