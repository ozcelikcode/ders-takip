# A21 — Admin settings and backups

17 October 2026. The owner asked to move on to the site settings and backup package. The whole memory bank and the existing code were reviewed first; the earlier catalog and user management changes were kept.

## Implemented behaviour

`AdminSettingsPage` uses a neutral `PageHeader`, panels and buttons, named section navigation, labelled fields and a visible save state. No private settings or backup query is set up for students. On a first private read error, editing the defaults is not offered; a retry is. At that time the page stated clearly that notification values were only stored and that there was no email or push delivery infrastructure. The displayed site identity is bound to the existing public branding source. No new formatter, dependency, schema or persisted data contract was added.

The form has a baseline and a draft snapshot. A pristine form follows new private reads; an edited draft is not reset by a refetch. Changing sections loses no other fields; the shared `siteSettingsSchema` validates the whole form. When an invalid field is in another section, a summary naming the field appears. Only normalised fields that differ from the baseline are sent with `settingsPatchSchema`; an unchanged form makes no write. This is not an optimistic version contract: last-writer-wins continues for the same field. When the person explicitly discards, the latest private snapshot is taken; an error keeps the input, and a successful save makes the response snapshot the baseline.

`settingsStore` applies an administrator read revision, a write revision and an account generation. An old private GET or error never overwrites a newer read or save result; a late write for an old account cannot update private or public memory. A public refresh error does not change the private settings read error. Private settings are never written to browser storage; the allowed public branding DTO is the only cache.

`BackupPanel` takes over backup listing. TanStack Query uses the account's `backups` key; loading, error, retry and a genuinely empty list are separate. The DTO type is defined in the frontend transport; the A19 runtime conversion of every backup response and request schema was not claimed. Restore opens only when `verified` is `=== true`; false, undefined and other values stay closed. Dates follow the viewing user's IANA time-zone preference. The manifest label does not replace the full checksum and schema check before a restore. The panel explains that the backup button creates a file on the server and does not download to the device.

Saving settings, a manual backup, restore and reset share a single `useAccountMutation` busy, epoch and mount boundary. While pending, section, setting, backup and reset controls are locked and double writes are rejected. Recovery and reset require saving or discarding an unsaved draft first. The shared `ConfirmDialog` waits for asynchronous success instead of the native `window.confirm`; errors stay inline and need an explicit retry; closing, Escape and double confirmation are locked while pending. An error from a cancelled earlier operation is not carried into the next confirmation; `useAccountMutation.clearError` was added for this real use.

The restore confirmation explains the safety snapshot of the current data, that the accounts, passwords and history in the backup come back and that every session is closed. After a successful restore the client signs out without refreshing the protected queries: the server has already revoked every session, so no refetch, 401 or new auth race is produced first. An error or an old-epoch response does not sign out. Logout closes every auth and cache boundary through the existing mechanism.

The `settings_only` confirmation states that only the settings are reset and that accounts, records and history are kept. The `all` confirmation states that every record (including administrators' records), student accounts, topics, progress, plans, sessions, measurement and settings are deleted, and that administrator accounts and backups are kept. A successful reset invalidates every resource of the account and clears and re-reads the private settings snapshot. The fixed delayed `window.location.reload` was removed. If the re-read fails, a read error with retry appears independently of the success; the default form is not shown.
