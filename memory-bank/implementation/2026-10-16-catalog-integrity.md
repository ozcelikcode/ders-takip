## A single write boundary

`services/catalog.ts` runs every catalog create, update, delete and reorder HTTP write in an SQLite IMMEDIATE transaction. The owner/global/administrator check, the related category and record, the name and order checks, the write and the response read are in the same transaction. So creating a new record while a category is moved, adding a topic while a record is deleted, and adding or archiving a topic during ordering are serialised at the same write boundary. No second implementation of the business rules was left in the controllers. The category controller's habit of adding internal database error messages to the response was removed; the central safe error mapping is used.

- **Deleting a record:** the related sessions' `courseId`/`topicId` links are cleared in the same transaction; only matching links change. The session save hook advances the optimistic `updatedAt`. Then a single record DELETE removes the active and inactive topics through the database cascade. Sessions, user notes, status, planned times and `SessionInterval` history are kept; an open measurement interval is not closed by itself. Writing with an old session snapshot gets 409. The nullable foreign keys also accept null in the model types; the column contract did not change.
- **Deleting a category:** a target is required for a non-empty category (409); the target cannot be itself (400), and a missing source or target gives 404. Every user's personal, global, active and inactive records move to the target, then the category is deleted. Record, topic and session identities are kept. A name conflict in the target with the same owner's or a visible global record gives 409; other owners' private records with the same name are valid. No stage commits partially.
- **Deleting a topic:** the existing `isActive=false` archive contract is kept; the topic, its session relations and measurement history are not deleted. On reactivation, if the active order conflicts and no explicit order is requested, it goes to the end. Active ordering does not change archived rows.
- **Create and update:** name conflicts and automatic topic order are protected inside check + write. A new topic's order is computed on the server; concurrent requests do not pick the same free slot. General catalog metadata edit and delete paths are last-writer-wins; no optimistic version contract is claimed for every resource.

## Shared contract and ordering

`contracts/catalog.ts` provides the shared Zod schemas and API write types. Positive safe-integer ids and orders, real booleans, allowed fields, name length, colour and the existing 5–480 whole-minute and difficulty rules are validated. Category, record and topic path ids are validated too. Converting every other list query and response DTO was not in this package's scope.

Reorder accepts only a unique `1..N` permutation of **all active topics** of a record. `expectedTopics` [{id, updatedAt}] is mandatory together with `topicOrders`. A shape, repetition or order error gives 400; a changed, incomplete, foreign or inactive list gives 409. The topic `updatedAt` hook advances by at least 1 ms over the previous value. Of two different concurrent orderings from the same snapshot, one gets 409; an ordering that changes nothing does not advance the timestamp. External SQL or bulk writers that do not apply the same hooks are outside this version guarantee.

The record detail and `includeTopics` responses carry `updatedAt`. The frontend enables drag only with all topics in ascending order; it disables it in filtered, descending or alternative orders and during pending and refetch. No fake optimistic order is shown before server confirmation, and the list refreshes after an error. An old open tab that does not send `expectedTopics` gets 400; the frontend and backend must be updated together and the tab reloaded.

After success or a 409, the catalog transport refreshes the current account's catalog and session query prefixes, so nested record, category and topic data in the calendar and activity also update. An epoch check stops a response for an account that has changed from triggering a refresh. A 409 produces no automatic mutation retry.

The `CreateTopicModal`'s unnecessary second query, which wrote a different response shape to the same key as the record detail, was removed. Guessing the order from the topic count was removed; the server orders. The form was aligned with the existing backend limit of 5–480 whole minutes. The record delete confirmation explains that study history is kept.
