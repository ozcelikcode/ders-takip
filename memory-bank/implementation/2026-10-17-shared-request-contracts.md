# A19 — Shared request contracts and plan boundaries

17 October 2026. The owner explicitly asked to continue with A19. The memory bank and the existing source were reviewed; the earlier A21 changes were kept in the working tree. No schema or data conversion, seed, reset, restore, real account or password change, commit, push or deployment.

## Findings and implementation

- The auth Joi middleware did not use the normalised value. Auth/profile and administrator create were bound to separate rules; administrator update did not go through a shared schema. Shared Zod 4 register, login, changePassword, profilePatch and managedUserPatch schemas and a user list query schema were added. The normalised body, query and params are passed to the controller; sections not named in the schema are not removed. The `any`-cast Zod parse result in the middleware was removed; adapting the Express query type to the numeric parse output stays at a single boundary.
- Public registration does not accept role, active or preference fields. Usernames are ASCII alphanumeric, 3–20; first and last names are trimmed, 2–50; a new password is at least 12 characters and at most 72 UTF-8 bytes. Signing in with an existing short password is supported; passwords are never trimmed. Administrator create defaults to an active student; **a patch produces no role or active default**. Null preferences and unknown fields are 400. A profile picture accepts HTTP(S) or base64 PNG/JPEG/WEBP/BMP supported by the existing UI, and empty or null to clear; an old stored picture is not rewritten when read.
- User, plan and backup path IDs are positive safe-integer strings. The user list rejects `1junk`, repeated query keys, unsafe offsets and disallowed sort or boolean values; the limit is at most 200. Silently turning bad input into another filter or page was removed. Permissions, self-admin protection, session revocation and preference transactions were kept.
- Auth register, login, me, refresh and profile responses and the administrator user responses come from a single `userResponse` projection. Passwords, ORM details and `legacyPreferences` never leave the server; nullable profile fields are consistent. Shared runtime DTO schemas validate auth/profile, administrator list and overview and backup responses on the client. A malformed response never becomes successful empty data, a zero or a new auth snapshot. The API user ID is a number; the frontend converts it to `String` explicitly at the auth view boundary.
- The backup reset body and restore ID are validated on the route; an invalid request creates no safety snapshot. The backup DTO does not return the host file path. `verified` must be a real boolean; when the field is missing, the client does not open restore. Create, list, reset and restore responses are validated; an acknowledgement missing `safetyBackupId` does not count as success. The snapshot, checksum, rollback and maintenance services were not rewritten.
- Validation error details are a field/message array through the shared `ApiError`/`ValidationIssue`/`validationError`; request values and Zod internals are not included. The old flattened error detail of settings was aligned with this format; the localized top-level messages were kept. The existing safe Sequelize 400/409/500 translation was kept.

## Plan versus StudySession

**A calendar entry is a StudySession. In the current API, a Plan is an optional dated goal container; a session can be linked explicitly with `planId`.** The calendar, sessions and timer work without creating a Plan. No automatic linking by date, mandatory Plan, new goal screen or goal generation from old data was added. Active state and the date range are the existing Plan goal scope; no new constraint forces a linked session into that range. An account that does not own a Plan cannot link a session to it. Historical links of an inactive goal are kept.

The Plan API is kept because of existing data, foreign keys and the measurement scope. The frontend `plansAPI` that no screen called and the duplicate `Plan`/`CreatePlanRequest` types were removed; there is no second client path presented as a calendar feature. New Plan management in the UI is not counted as product scope.

The shared create, update, query, goals and `PlanRecord` schemas replaced the local route schemas. Date-only ISO input is kept as UTC midnight; ISO with an offset is accepted, and ambiguous local or fuzzy dates are rejected. The end must be after the start. A partial date change is checked together with the current row. A goals patch merges with the current JSON and does not delete other goal fields. The existing numeric `targetTopics` contract and the inclusive date boundary were kept.

`services/plans.ts` is the single IMMEDIATE check and write boundary: create, date change and reactivation check active plan overlaps atomically; of two identical concurrent creates or moves into the same free range, only one succeeds. Overlap is 409, bad input 400 and a foreign or missing record 404. Plan metadata is last-writer-wins for the same field; no optimistic version was added. The response DTO is validated inside the write transaction.

Plan deletion detaches linked sessions with an instance save; `planId` becomes null and the session `updatedAt` advances. Notes, status, plan times, duration and measurement records are not deleted. An old open session editor gets 409. Plan delete and detach are one transaction; an error even after the last DELETE rolls everything back. List, detail and stats limit nested sessions to the owning user. Plan stats use the existing measured-time service; embedded persisted session metadata is not presented as measurement. External SQL writers are outside the domain and version guarantees.

## Frontend forms and the dependency boundary

The sign-in and registration RHF forms run the shared schemas through `contractResolver`; the schema copies were removed. Profile and password submissions use the shared schemas. A late password-change response for an old account does not sign out the new account (auth epoch check).

The session view schema moved to `sessionForm.ts`; the date, time and category view fields are not an API DTO. When the request is built, the shared `createSessionSchema`/`updateSessionSchema` validate it separately. Session type and Pomodoro settings come from the shared source. The form's 5–480-minute limit was removed; the server's real 1–1440-minute limit is used through the shared `sessionDurationLimits`/`isSessionDurationValid`. Valid fractional minutes are kept; a real range over 24 hours or under 1 minute is not sent. The calendar resize's 5-minute snap and minimum UX stay separate from this API limit. Splitting the form's render fields into smaller components remained general maintenance; no second view/request engine was created.

The existing preferences runtime schema moved from `index.ts` to `preferences.ts`; public export names and the persisted v1 JSON did not change. The old Joi validation file and the Joi package were removed. The last Zod 3 form in the frontend moved to Zod 4; all three workspaces resolve the same 4.6.7. `contractResolver` passes nested field errors to the existing RHF and does not use the old major resolver path. A clean `npm ci` passed with the root lock kept. Audit: 12 affected package nodes (5 high / 7 moderate / 0 critical); this package did not close the whole dependency backlog.
