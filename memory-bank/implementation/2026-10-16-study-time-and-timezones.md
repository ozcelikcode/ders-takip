# Real Study Time and Time Zones — 16 October 2026

## Scope and data policy

The owner asked to continue with the next package. A09 and A16: separating planned duration from measured duration, study, break and pause intervals, and calendar and report correctness in the user's time zone. The earlier A07/A08 implementation is kept; no commit, push or deployment.

`duration` stays the planned minutes in the existing contract. `startTime/endTime` are planned times and do not move with real work. The new `SessionInterval` table keeps `study`, `break` and `pause` intervals on the server for every start, resume, phase, pause and completion. A partial unique index ensures one open interval per session. Closing an interval and updating the session happen in the same IMMEDIATE transaction; on an error injected after the SQL, both roll back together. The client cannot write a duration value.

`trackingCoverage`: a new session is `complete`; a session from before 004 is `untracked`; if measurement starts on such an old session it becomes `partial`. No study intervals are derived from old planned durations. Old identities, notes, passwords, plans, times, durations and states are kept. A new session marked completed without ever being started has zero measured study. Old unmeasured or partial rows are flagged separately in summaries.

Reopen, reset and cancel never delete earlier measured intervals. Starting again adds a new interval; earlier work never disappears from reports. Really measured study of a cancelled or not yet completed session is included in totals. The completed session count is a separate metric. An open pause is measured as pause, not break. A separate break session does not enter the study total. GET computes an open interval up to the server's `asOf` time without writing to the database. Closed intervals are fixed; if the wall clock goes back, the last recorded interval boundary is kept and no negative duration is produced.

This measurement is the server-confirmed wall-clock range of an active session; it does not measure a person looking at the screen. If the network drops or the browser closes, a pause or complete that never reached the server is not invented retroactively. Deadline, reload, tab ownership and interruption policies were still needed under A15 at that time.

## Schema evolution

The explicit `004-session-activity-intervals`: adds only `trackingCoverage` (default `untracked`) to the existing `study_sessions` table and creates `session_intervals`. The new model's create default is `complete`. Pre-validation accepts as missing only the known column of this pending migration; other gaps are rejected. The migration is transactional and idempotent; if creating the interval table fails, the added column and the migration record roll back. Startup runs no sync or alter, and the API does not start with a pending migration.

The new table's session foreign key cascades. Session deletion and reset work within their existing scope; the new table does not escape it. Snapshot validation also requires the new migration and columns. Snapshots from 003 or older are kept but rejected by the current restore; they need a compatible version or a controlled migration on a separate copy.

## HTTP and reporting

The session DTO contains `studySeconds/breakSeconds/pauseSeconds`, `trackingCoverage`, `activityIntervals` and `asOf`. Recorded intervals have millisecond precision; totals are in seconds. `activityKind: study|break` can be used only with an in_progress target. A phase change advances the optimistic version even when the session status stays the same. A dedicated break type cannot be recorded as study. The transition table and `expectedUpdatedAt` are kept.

`GET /study-sessions/stats`: measured totals within the current user's scope and a daily breakdown for an optional date range. A date range needs both ends together and at most 366 days; an all-time query has no day list. Duration is the real interval's intersection with each day; it is not written in bulk to the planned start or the completion day. A single read transaction and a single logical `asOf` are used. The authorised `/users/:id/stats` uses the same account with the self/administrator boundary. The old path in which the administrator user list queried the administrator's own sessions for every user was removed; global administrator dashboard totals were separately open under A17.

The dashboard, weekly chart, plan stats, recent activity and notification durations and user management use measured time. Planner card and form durations are planned values. An error is never shown as zero data; unmeasured historical rows are not added to measured totals. A plan's goal ratio is computed from the real study total; the duration total of unfinished plans does not count as study.

## Time zones and the calendar

Luxon 3.7.2 and its types were chosen; it uses the runtime's Intl/IANA data. The [official API](https://moment.github.io/luxon/api-docs/index.html), `startOf`/`plus` and `getPossibleOffsets` behaviour were reviewed. A Temporal polyfill was considered but not added to the project. `packages/contracts/time.ts` is the single day and time contract; the time-zone schema is shared between preferences and queries.

API instants are ISO with an offset or Z. Calendar query days are strict `yyyy-MM-dd` and are converted to a `[start of day, start of next day)` UTC range with the user's preferred time zone or an explicit query time zone. The backend process TZ is never used. Listing takes the intersection with the planned range; an overnight session also shows on the second day. Day boundaries are never produced by adding 24 hours; 23/25-hour DST days are tested.

The form converts wall time → instant in the selected time zone. Missing or repeated hours are never moved silently to another hour; the form shows an explicit error. Existing instants with an explicit offset can be read; the grid does not produce a separate hour row for the two copies of a repeated hour. Two overlapping wall-clock cards on a DST day and the full pointer and keyboard flow were to be evaluated separately in the browser under A22.

`CalendarDate` is a synthetic UTC `Date` adapter that carries only calendar fields; it is not a real instant. `frontend/utils/calendarDates.ts` computes days, weeks and months on these fields; the browser's own DST cannot disturb the selected time zone. **`CalendarDate.toISOString()` is never written to the API**; it is converted to a real UTC instant with `calendarViewInstant` or `wallTimeToInstant`. Durations are computed on real instants. The daily and weekly views and the move-to-date dialog use these adapters; an overnight card is clipped to the visible boundary of each day. A time-zone change rebuilds the calendar state; the UI shows the selected time zone.
