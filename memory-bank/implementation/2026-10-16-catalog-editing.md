# A21 — Catalog editing and recovery UI

16 October 2026. The package for students managing their own private records and topics was completed. A17, A18 and A24 and the shared planner, completed with other tools, were not re-applied.

## Implemented behaviour

- `CoursesPage` and `CourseDetailPage` show edit and delete actions to the owner of a private record or an administrator. A shared catalog or another user's catalog never opens editing to a student. `lib/catalogAccess.ts` shares the view policy; the server is the final permission boundary. The card link and the action buttons are siblings; there are no nested links or buttons.
- `CourseEditorModal` is the single implementation for student create/edit and administrator create/edit. An administrator's new record still defaults to shared; the active and shared controls are for administrators only. The old `CourseCreateModal` and the second `CourseModal` inside administration were removed.
- `TopicEditorModal` is the single create/edit form; the old `CreateTopicModal` was removed. The shared contracts Zod 4 schemas are used directly; the duplicated Zod 3 schema and resolver in these forms were removed. Clearing a description is sent explicitly as an empty string. English technical names and the persisted Turkish difficulty values are kept.
- Editing sends only changed fields. The form never rewrites a topic's course, order or `isActive`. Opening the form and saving without changes produces no HTTP write. A background refetch does not reset the draft. An unknown existing icon and an existing category that dropped out of the active category list are preserved.
- `CatalogEditorDialog`: a Headless UI focus and Escape boundary, labelled fields and errors, a fieldset and close lock while pending, and a visible server error. `useCatalogMutation` prevents double submission; after success it refreshes the account catalog, sessions and topic-progress prefixes. A response from a previous auth epoch produces no success toast, cache change or close callback. An error never retries the write automatically, and the draft stays open.
- `CatalogDeleteDialog` explains permanently deleting a record and archiving a topic separately. The record with its topics and topic progress is deleted; sessions, notes and measured interval history are kept, and the related foreign keys are cleared. Archiving a topic deletes no rows. The asynchronous confirmation waits for server success and stays open on error.
- `CourseDetailPage` queries the archive with `isActive=false` only when an authorised user asks. The archive view has no reorder or progress writes; editing and restoring are available. After a restore the active catalog and the user's progress are read again. The progress summary counts active topics.
- `AdminCoursesPage` uses the same editor, confirmation and icon system; the earlier large inline modal and duplicated icon maps were removed. The record list, detail, administrator record management and catalog dialogs follow the neutral panel and typography direction. Colour marks identity only in the small record icon. Drag handles got an accessible name that includes the topic name.

## Restore integrity fix

Restoring from the archive checks active name conflicts inside the transaction even when the name is unchanged. If another active topic now uses the archived name, it returns 409 with no partial change. The archived row can be renamed to a unique name and then restored. Two concurrent restores with the same name end with 200/409. No schema or migration change was needed.

## Limits and next steps

The A21 student catalog UI package was closed. The neutral design consistency of the remaining category, user and settings surfaces and other modal and administrator surfaces was not closed as a whole yet. There was no full WCAG, mobile, touch or automated browser evidence. Metadata writes keep the existing last-writer-wins contract; a dirty patch reduces lost-field writes but is not an optimistic version contract. Reorder keeps the existing full snapshot and version rule. A19 (DTOs and the meaning of Plan), A22 and A04 remained open.

The temporary browser sessions were signed out, the tab, API and preview were stopped, and the temporary SQLite folder and the `.local` fixture script and pointer were removed. The single real dev server was left on localhost:3000 / API 5002; the real administrator password was never read or changed. Schema 006 and the existing private backup and snapshot pointer files were kept. No commit, push or deployment was made.
