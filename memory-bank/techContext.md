## Startup and configuration

- `src/app.ts` exports the middleware, routers and HTTP application; importing it starts no listener or scheduled job.
- `src/index.ts` starts the server and scheduled jobs after the environment, database and schema checks. On SIGINT/SIGTERM it stops jobs, waits for requests to finish and closes the database.
- `src/config/environment.ts`: the central Zod schema: `NODE_ENV`, `PORT`, a `JWT_SECRET` of at least 32 characters, an access lifetime of at most 15 minutes, `SESSION_TTL_DAYS` of 1–30, `BCRYPT_SALT_ROUNDS` of 12–16, positive limits, `DB_PATH`, `BACKUP_DIR`, `BACKUP_COPY_DIR`, `AUDIT_LOG_PATH`, SMTP and VAPID settings. A production `FRONTEND_URL` must be HTTPS. The old `JWT_REFRESH_SECRET`/`JWT_REFRESH_EXPIRE` are not used.
- Startup stops on a missing, weak or example JWT secret; there is no fixed-secret fallback. Environment values are never copied into error messages.
- `PORT` defaults to 5002; CORS comes from `FRONTEND_URL`. The production rate limiter defaults to 100 requests per 15 minutes. Header and URL checks of the deployment are needed separately.
- `npm run configure` creates `backend/.env` only when it does not exist, with a random signing secret and 0600 permissions, and never changes an existing file. The owner's first-setup authorisation created a new `.env` and database (there was no existing installation), and the administrator CLI created `admin@example.com`; the private password is in `.local/admin-password.txt` (0600, Git-ignored) and the values are not documented.
- The frontend API base defaults to `/api`; the development proxy forwards to backend port 5002. A production reverse proxy is the deployment's responsibility.

## Database lifecycle

- `database.ts` resolves `DB_PATH` relative to the backend root or uses an absolute path; `:memory:` is supported separately. Backups use the same `databasePath`/`backupDirectory` source.
- `connectDB` only authenticates. No `sync`/`alter`/`force` and no `_backup` table cleanup at startup.
- `database/migrations.ts` runs the migrations `001-initial-schema` through `013-tags` with the `schema_migrations` table: `002-auth-sessions`, `003-user-preferences-v1`, `004-session-activity-intervals`, `005-pomodoro-clocks`, `006-user-topic-progress`, `007-password-reset-tokens`, `008-personal-categories`, `009-notifications`, `010-session-series`, `011-course-goals`, `012-calendar-feeds` and `013-tags`. Only the explicit `npm run db:migrate` command writes (008 rebuilds the category table, so it runs in its own transaction on the main connection with foreign keys off and runs `foreign_key_check` before committing); the baseline creates the first tables with a non-destructive sync inside a transaction and keeps existing rows.
- If an existing model table lacks a column, a dedicated migration is required; no silent alter happens. Future schema changes are added as new migrations. The first baseline is not a general legacy schema repair tool.
- The development seed runs only in development with explicit `ADMIN_EMAIL`/`ADMIN_USERNAME` and an `ADMIN_PASSWORD` of at least 12 characters. It uses `findOrCreate` in a transaction; existing accounts, passwords and categories are never reset and the password is never logged.
- Migrations, seed, reset and restore are never run on the user database for testing. Tests create and remove their own SQLite file under `mkdtemp`.

## Models and API

Twenty-two models: User, Category, Course, Topic, Plan, StudySession, SessionInterval, PomodoroClock, UserTopicProgress, Settings, Backup, AuthSession, RefreshCredential, PasswordResetToken, NotificationDelivery, PushSubscription, SessionSeries, CourseGoal, CalendarFeed, Tag, CourseTag and SessionTag. Data fields, tables and the localized difficulty values were not renamed. Categories are global or personal; a Course is personal or global; a Topic belongs to a course; Plan and StudySession belong to a user. Settings are global key/value pairs; `User.preferences` is the personal JSON.

- Auth: `/api/auth/register`, `/login`, `/refresh-token`, `/logout`; `/me`, `/profile`, `/change-password`; `/account/export`, `/account/import`, `DELETE /account`. The access JWT lives only in memory; `sid`/`id`, explicit HS256/issuer/audience validation and database session, active-status and role checks. The opaque refresh credential is stored only as a hash in the database and travels in an `HttpOnly`/`SameSite=Strict` cookie, `Secure` in production. A custom `X-Requested-With` header and origin checks apply.
- Refresh rotates inside an IMMEDIATE transaction; reuse revokes the whole family, and the session lifetime is absolute. Logout, password change, administrator recovery and role or status changes apply revocation. New passwords are at least 12 characters and at most 72 UTF-8 bytes. Login and password change check stale-hash races inside transactions.
- The `admin:manage` CLI creates or recovers only with an existing, ready database and a private password file; create works while no administrator exists, recover works for an active administrator by exact email. It never promotes a student and never logs the password. Tests use temporary databases.
- Course visibility lives in `policies/courseAccess.ts`: owner, global or administrator. Lists, a single record, a record's topics and topic parent joins use this scope. The 18 October cleanup removed the `GET /categories/:id`, `GET /topics`, `GET /topics/:id` and `GET /users/:id` endpoints the frontend never called (routes, controllers, client methods and tests); topics are read through `GET /courses/:id/topics` and `GET /topics/progress`, and user stats through `GET /users/:id/stats` (self/admin boundary). The PUT and DELETE endpoints did not change.
- For a new StudySession, the plan owner, course and topic visibility, active status and topic-course consistency are validated. When only a topic is given, the accessible parent course is resolved.
- A StudySession GET has no side effects; it never updates notes or status.
- Create, update, action and delete run in IMMEDIATE transactions in `services/studySessions.ts`. A mandatory `expectedUpdatedAt` and monotonic timestamps give stale 409s, with the shared state policy and a single running session. Paused and completed sessions reserve their time; cancelled ones free it. The shared session Zod schemas live in contracts. Real duration is implemented with study, break and pause intervals and IANA day boundaries; old faulty relations or overlaps in the real database were not scanned or changed.
- `GET /settings` returns only the public branding DTO; `/settings/admin` and PUT are administrator-only and `no-store`. Writes use an allowed key/type schema inside a transaction. `allowRegistration`/`maintenanceMode` are in the public DTO and enforced in register, login and `protect`; `sessionTimeout` is the idle limit enforced in `rotateAuthSession` (`maxStudentsPerCourse` was removed). `services/siteSettings.ts` is the single source for reading settings. Backup routes are administrator-only: the native SQLite backup API, an external manifest with SHA-256, integrity, foreign-key and schema checks, a safety backup, an atomic destination restore with rollback and the maintenance gate are implemented. The `settings_only`/`all` resets are transactional, and restore and both resets require the administrator's password. A job every 5 minutes re-reads the setting and counts 1, 5 or 7 full days; the newest 14 automatic snapshots are kept and `BACKUP_COPY_DIR` receives copies. The single-backend-process limit, off-site copies and capacity remain open.
- Administration: `GET /users/admin-stats` (global summary) and `GET /users?includeStats=true` (bulk user summary) use `getAllTimeSummaries`, administrators only. Topic progress: `GET /topics/progress`, `PUT /topics/:id/progress` (per user). The activity log: `GET /api/admin-audit`.
- The central error handler maps Sequelize `ValidationError` to 400 and unique and foreign-key errors to 409; unexpected error messages are never sent to the client. The old MongoDB error mappings were removed. Auth, user, plan and backup input validation was unified in contracts and the `validate` boundary; error details use the shared field/message shape.

## Frontend

- `lib/locale.ts` is the single source for locale settings (app locale, date-fns locale, weekday labels, browser time zone). The week start is read with `useWeekStart()`/`resolveWeekStart`; registration sends the browser time zone.
- Bundling: contracts ESM with `sideEffects:false`; Luxon only in `zonedTime.ts` (the schema modules are Luxon-free); a Vite `icons` manual chunk; the Layout and chart are lazy (the dashboard chart is requested once its data arrives; the opened page loads together with the Layout via `shellPages` in `App.tsx`); the page switcher loads on first use. The session refresh starts in an inline script in `index.html` and the first `refreshToken` call takes it over (`lib/initialSessionRefresh.ts`); inline scripts must be allowed by the production CSP. The API base lives in one place: the `define` in `vite.config.ts` (`import.meta.env.VITE_API_BASE_URL`, default `/api`; `%VITE_API_BASE_URL%` in `index.html` reads it too). The build adds a preload for the Geist latin-ext font to `index.html` (`preloadTurkishFont`; the build stops if the file is missing). `POST /auth/refresh-token` returns 204 without a cookie (the client treats it as 401 `sessionExpired`) and 401 for an invalid cookie. A production server must serve JS and CSS with gzip or brotli (the measurement fixture uses gzip). React Router 7.
- Password reset: `services/passwordReset.ts` plus `services/mailer.ts` (nodemailer, optional SMTP environment); without SMTP an administrator issues a one-time link.
- The displayed core concept words (course/topic/session) derive from the site or personal `terminologyPreset` or `customTerminology` through `resolveTerminology` and `useTerms()`; the word and suffix logic lives in `packages/contracts/src/terminology.ts`. Screens never hard-code these words.
- App pages load through lazy imports and Suspense. The ErrorBoundary sits at the root; on error it shows a recovery screen and never reveals internal error details. Source maps are off in the build.
- The QueryClient lives in `src/lib/queryClient.ts`. The auth store clears the cache and old queries on an identity change; late-response isolation is tested. All resources take their keys from the account factory, and session views also carry the time zone and date. The current day refreshes every 30 seconds and on focus, and writes invalidate every related summary by prefix. Preferences live only in the current user's memory and on the server; read notifications are stored per account.
- Auth works with a single in-memory source, a refresh promise and an epoch; late responses can never bring back a finished or changed account. A late 401 is retried with the current token. Cookie changes are serialised through a separate transport and Web Locks; BroadcastChannel clears other tabs' cache and identity. For an offline logout, a pending intent without secrets is kept; in that state a reload does not refresh. The old auth storage is cleared.
- Preferences v1 derive from the shared schema; `/auth/profile` and the administrator patch load and merge the row inside an IMMEDIATE transaction. Migration 003 converts the old JSON and keeps the original in `legacyPreferences`; the API never exposes the archive. An invalid future version rolls back the whole migration. Orphaned old browser values are kept in the `unassigned-account-state` archive and applied to no account.
- `WeeklyPlanner`/`DailyCalendar` use one `PlannerCalendar`/`usePlannerCalendar`/card/geometry; the second command engine was removed. `PomodoroPage` and the modal show the persistent server clock through a single `usePomodoro`/`PomodoroTimer`.
- Seven unreachable modules were removed: AdminScheduleManager, CourseManagementModal, AddTopicModal, EditTopicModal, GoalSettingModal, AdminCategoriesPage and the `pages/courses` placeholder. The records page in use is `pages/CoursesPage.tsx`.
- The chart's internal hour and minute keys are `hours`/`minutes`. The fixed demo account list on the sign-in page was removed.

## Persistent Pomodoro (16 October)

A15 implemented: the Pomodoro page and the planner modal share a single `usePomodoro`/`PomodoroTimer`. Phase, cycle, remaining milliseconds and the absolute deadline are stored in the `005-pomodoro-clocks` table; the number of browser callbacks is not a duration. The server scheduler advances the phase at the persisted deadline. Automatic breaks are opt-in; work never starts by itself after a break. Reloading, closing the modal or changing routes does not stop the timer. An unknown phase is never invented for an old row; the person activates the timer explicitly.

Commands run with `expectedUpdatedAt` in the shared IMMEDIATE session transaction; the general planner actions follow the same rule. Before a late worker runs, GET and stats cap open study and break time at the deadline and do not write. Reset never deletes the person's notes or measurement history. The scheduler stops at the maintenance and restore gate and in-flight work is drained. Numeric and string id normalisation in the account key, version and epoch protection, and a cross-tab invalidation notice that carries only the account id exist.

The real local 005 upgrade was completed with a private native snapshot, a preservation comparison of every old table row and a manual current-schema backup with id 5; no seed, reset or restore. The single root dev server runs on localhost:3000 and API 5002. Test and production-fixture evidence and limits: `implementation/2026-10-16-pomodoro-continuity.md`.

No new dependency. Migration 005 is mandatory at the startup and snapshot schema gate; an old snapshot is not loaded by the current restore without a controlled upgrade on a separate copy. The root check passed with 175 tests, type checks, lint and build. The server wakes every second and runs a transaction over the oldest 100 due clocks; after a long outage at most the finished work phase and the chosen break are completed, and no fake work cycles are produced. The client renders every 250 ms; the detail refetches every 30 seconds (2 seconds when due) and on focus and reconnect, the list every 60 seconds. No load test was done.
